PLAYLIST
========
Writing a DOS Game from Scratch — C & Assembly

Playlist description:
------------------------------------------------------------------------------
Building a DOS game the way these machines were actually programmed — one
constraint at a time, in C and assembly, with nothing at all between the
program and the hardware.

No engine, no framework, no library to call. In DOS one program owns the whole
machine, and the screen is memory: write a byte to the right address and it is
on the glass. Every episode starts from that and adds one thing, and every
episode ends with something on the screen.

Where it goes: a single pixel, then why the picture tears when it moves and the
second screen that fixes it, then a point in 3D and why the arithmetic has no
decimal point in it, a line, a box, a city of them, a camera built out of sine
tables because there is no floating point worth using, a flight model, and
instruments that mean something. By the end it is a wireframe flight simulator,
because that is what this code actually is — the lessons are cut out of a real
one, not written for a tutorial.

The constraints are the teacher. No floating point. No memory to spare. One
64K segment, and it runs out. Everything interesting in here is a consequence
of something the machine would not do, and most episodes contain a mistake
that really happened and what it looked like on screen when it did.

Why bother, in this decade? Because these machines are still running. Tills,
production lines, dispatch desks and accounting rooms are full of software
written this way, still in service, and the people who know how it was built
are retiring faster than it is being replaced. This series is that knowledge
written down while it can still be demonstrated rather than described.

Tools: DOSBox, Open Watcom C for the first lessons, flat assembler after that.
All of it free, all of it open, and all of it running on a modern machine. The
assembler ships inside the source repository, so from the second lesson on
there is nothing at all to download.

DESCRIPTION
===========
On a DOS machine there is no graphics library to call. The screen IS memory:
write a byte to the right address and it is on the glass. This first lesson
does exactly that, in C, with nothing in between.

No driver, no output function, no permission asked. Two addresses do all of
it:

  0xB800  the text screen — 80x25 cells, two bytes each: the character, and
          then its colour
  0xA000  mode 13h — 320x200 in 256 colours, one byte per pixel, and that byte
          IS the colour

We write HELLO straight into the text screen without printing it — nothing is
cleared, because nothing was printed — then switch to 320x200 and build up a
pixel, a line, a line in another colour, and a square, all out of the same two
lines of code.

The word that makes it possible is "far":

  unsigned char far *vga = (unsigned char far *) 0xA0000000L;

An address on this machine is two numbers, not one — a segment and an offset
inside it — and "far" is C saying so out loud. Everything in this series that
looks strange later comes back to that.

And then the part everything else leans on: WHICH byte, exactly, and why the
corner is the TOP left one, when every graph ever drawn puts nought, nought at
the bottom. Because offset zero is the first byte of the segment - and because
the electron beam swept the glass from left to right, dropped a line and swept
again, from the top down. The bytes are simply in the order the beam needed
them, and every canvas since has counted from that corner.

  x = 5, y = 0   ->  offset = 5
  x = 0, y = 1   ->  offset = 320
  x = 5, y = 2   ->  offset = 2 * 320 + 5 = 645

Source (runs on its own, nothing else needed):
https://github.com/KirinDenis/wire-city-2/blob/main/LESSONS/L01/MEMORY.C

Tools: DOSBox 0.74-3 and Open Watcom C — free, open source, and it still
builds 16-bit real-mode DOS programs today:

  wcl -0 -ml -bcl=dos MEMORY.C

From the next lesson on, the assembler ships inside the repository and there
is nothing left to download at all.

On the dates: mode 13h and the VGA card arrived in 1987, and the text screen at
0xB800 is older still. Any compiler that can build a 16-bit real-mode DOS
program does every line of this identically — the tool matters far less than
it looks.

And the diagrams in the opening were drawn by the same program - the same far
pointer, the same y * 320 + x, the same video BIOS for the text. There is
nothing on screen in this video that the video does not explain.

Assembly comes next in this series, and it changes none of this. It only makes
it fast enough to do sixty thousand times a second.
